## 2. 状态码从哪里来

### 支付宝 SDK

`PayTask.payV2()` 返回的 `resultStatus` 是支付宝定义的字符串码，客户端原样记录：

| resultStatus | 含义 | 客户端结果 |
|---|---|---|
| `9000` | 支付成功 | 继续调用 `trans/confirm` |
| `8000` | 正在确认（结果未知） | 显示失败/待确认，不伪造成功 |
| `6001` | 用户中途取消 | 显示「支付宝未完成支付（6001）」 |
| `6002` | 网络连接错误 | 同上 |
| `4000` | 订单支付失败 | 同上 |
| `5000` | 重复请求 | 同上 |
| `6004` | 支付结果未知 | 同上 |

日志格式（logcat tag `SmartLife798/Evidence`）：

```text
prepay.ok billId=... payType=21 orderBytes=...
alipay.result resultStatus=9000 memo=...
alipay.outcome billId=... success=true resultStatus=9000
confirm.ok billId=...
```

> 不记录 orderInfo 原文（含商户签名），只记录长度与状态码。

> 这些日志只在 **debug** 构建输出（`Diag.event` 在 release 中为空操作），
> 所以上面的抓取步骤必须使用 `assembleDebug` 产物。release 包不会写业务日志。

### 服务端启停

```text
dev.start.accepted did=... ptype=21 dtype=6
dev.start.confirmed did=... state=启动中
dev.end.ok did=...
dev.start.fail did=... ptype=... code=-52 msg=...
```

业务码映射（`core/Api.kt`）：

| code | 含义 | 客户端行为 |
|---|---|---|
| `-52` | 有未付款/付款失败账单 | 拉取最近一笔未付账单，切订单页并打开支付面板 |
| `-88` | 需要先完成支付 | 同上 |
| `-87` | 余额不足 | 提示余额不足（不自动扣款） |
| `-99` | 登录过期 | 退出登录 |

> **响应信封**：原应用的 Retrofit 声明是 `BaseReq`（`data` 为 `Object`），说明命令接口的
> `data` 不是固定对象。本客户端把信封与 `data` 分开解析：`Unit` 端点接受
> 字符串 / 数字 / 数组 / 对象 / null。热水机反馈的「响应解析失败」正是旧实现按
> `ApiResp<Unit>` 整体反序列化、遇到 `data:""` 时抛 `Expected BEGIN_OBJECT` 导致的。
> 该结论有静态依据（`c4/h.java` 的 `BaseReq` 声明）与单测覆盖，但**热水机真实响应形状未用
> 真实账号抓包复核**。

### 计费字段

`dev/end` 成功后，服务端在 `bill/lst-owner` 生成账单。客户端记录：

```text
bills.page page=1 count=6 unpaid=0 statuses=3,3,3,3,3,3
```

单笔账单的关键字段：`id / ctime / utime / payment / discount / status / type / cata / dir / msg / dev{id,name,bm.dtype} / prds[]`。
`status=3` 为已付款；`1/4` 为未付款/失败；`2` 为待确认；`5` 为核算中；`9` 为已取消。

## 3. 实测步骤

### 3.1 支付宝

1. 在用户授权后选用已有待支付账单，不为测试自动制造消费。
2. 本客户端「订单 → 待付款 → 去支付」，选择支付宝。
3. 记录 `prepay.ok`。
4. 在支付宝收银台完成支付（或取消）。
5. 抓日志：
   ```powershell
   adb logcat -c
   # 操作支付
   adb logcat -d -s SmartLife798/Evidence
   ```
6. 保存状态码与脱敏摘要至 `evidence/alipay-<时间>.log`，不能原样保存 SDK result 或签名串。

### 3.2 设备 start/end

1. 确认设备在线：详情页显示「在线」且按钮为「立即使用」。
2. 用户授权后点「立即使用」，分别观察 `dev.start.accepted` 与 `dev.start.confirmed`；仅受理不能报已启动。
3. 再点「结束使用并结算」，等待 `dev.end.ok`。
4. 立即打开订单页，确认新增账单；抓 `bills.page` 与账单详情。
5. 把脱敏后的 `dev.start/end` 日志与账单摘要写入 `evidence/device-<设备号>-<时间>.log`。

## 5. 启动链路实测（2026-10-21，真实账号）

设备：`861089059737339`「茂师实训楼4楼冷」，dtype=5，`bm.brand=康之源 / model=SK-450-1`，
`ntype=9`，`subs` 两路（`out` 0.226 / 6111.153 升），`payItems=[91,21]`，`wallet.total=0`，
企业 `dmode=1 / emode=41`，二维码 `https://i.hnkzy.com/q/1/861089059737339`（解码得到，服务端
`qr/use` 返回 `type=3` + 该设备）。

| 步骤 | 实测结果 |
|---|---|
| `dev/start?rcp=true&ptype=91` | `code=0`，`data` 为 302 位设备帧；`dev/status` 连续 6 次 `gene.status=99`，机器不动作 |
| `dev/start?rcp=false&ptype=91` | `code=0`，`data=""`；**2 秒内 `gene.status` 变为 `1`** |
| 客户端（v1.2.6）扫码 → 手动输入该二维码 → 自动启动 | `dev.start.accepted … data=`；`dev.start.confirmed state=启动中`；首页卡片显示「启动中 / 已授权取水」 |
| 未按机身「启动」直接 `dev/end` | `code=-2`「设备运行中,请在设备上点击结算」，随后 `gene.status` 回到 `99`，生成 `status=3 / payment=0.0` 的账单 |
| 结论 | **根因是 `rcp`**：`rcp=true` 时服务端只回执、不下发执行；`rcp=false` 才会真正把机器拉起来 |

> 该机型是「扫码授权 + 机身按键取水」的水控器：App 启动后机器进入 `1`（已授权），
> 需要按机身「启动」取水、按「结算」结束；`dev/end` 在运行中会被服务端以 `-2` 拒绝。
> 客户端已按此实现提示与 `-2` 的处理（保留记录、等待回到 `99`）。

### 支付宝支付

同次采集记录中 **没有待支付账单**（`bill/lst-owner` 的 6 笔全为 `status=3`，含本轮两次 0.00），
因此无法在真实账单上完成一次支付宝扣款。已验证的接口事实：

```text
GET /bill/pay/channels?id=<billId>
-> code=0, channels=[{type:21, name:"支付宝", seq:91, imgUrl:"https://i.hnkzy.com/public/images/pay/alipay.jpg"}]

GET /trans/prepay/21?id=<已支付账单>
-> code=-1, msg="您的账单状态已改变，请退出后重试"
```

即：渠道查询可用、`prepay` 对已结算账单会正确拒绝；`trans/prepay/21 → 支付宝 SDK → trans/confirm`
链路仍**未做真实扣款**，需要一笔 `status=1/4` 的账单（该校企 `dmode=1` 为记账模式，消费账单会
自动结算为 0.00）。不要用模拟数据冒充支付成功。

## 6. 分页坑（已修复）

`bill/lst-owner` 的 `page` 是 **0-based**。原实现传 `page=1`，服务端把第一页当第二页，返回空列表，于是「消费记录」看起来没有云端数据。修复后：

- UI 第 1 页 → API `page=0`
- UI 第 2 页 → API `page=1`
- 已用真实账号验证：`page=0` 返回 6 笔，`page=1` 返回空。

### 根因对比

同一已登录账号、同一在线待机饮水机（仅记录尾号 **5859**），请求固定为 `dev/start`，`upgrade=true / ptype=21 / args="" / rcp=false / cnt=1`。每个版本只发送一次对比请求，没有自动重试：

| 版本头组合 | 服务端与设备结果 |
|---|---|
| `VersionCode=3.1.5` + `Android_ilife798_3.1.5` | 详情 `code=0`；启动 `code=-1 / 请升级最新版APP`，`data=null` |
| `VersionCode=3.1.7` + `Android_ilife798_3.1.7` | 启动 `code=0 / data=null`；首次快照仍为 `99`，后续变为 `1`；`dev/end?rcp=false` 返回 `0`，后续回到 `99` |

结论：旧官方版本标识触发**启动端点**门禁。这个对比同时改了 VersionCode 和 User-Agent，不能据此断言服务端只检查其中一个头。详情可读或更新查询返回“无需更新”均不能代替启动兼容性验证；原应用更新通道、新样本签名及排查表见 [docs/04](04-接口契约与变更检测.md#6-原-apk-版本与更新通道)。

结束后账单列表最新出现一笔 `status=3 / payment=0.0` 的饮水类账单，但列表中的 `dev` 仅带 `bm`、不带设备 id，未据此声称完成了该设备账单逐笔归属确认、现场出水或非零结算。不要用原始列表导出账号信息。
