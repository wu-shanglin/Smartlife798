## 1. 验证前提

- 支付需已有 `status=1/4` 账单、可用支付 App 与具体业务授权；设备启停需在线设备、具体授权及现场按键配合。
- 不为测试自动发短信、创建充值单、签约、支付或启停。GET 和错误路径不代表无副作用。
- 脱敏证据存于忽略的 `evidence/`；禁止 token、手机号、签名订单、原始 SDK result/memo 或异常文本。示例不是实测输出。

## 2. 状态码从哪里来

### 支付宝 SDK

`PayTask.payV2()` 返回字符串 `resultStatus`。当前桥只保留下列白名单码，其余映射为 `unknown`；日志与显示使用固定提示，不回退原始回执。

| resultStatus | 含义 | 客户端结果 |
|---|---|---|
| `9000` | SDK 支付完成 | 继续 `trans/confirm`，以服务端确认为准 |
| `8000 / 6004` | 处理中或结果未知 | 提示核对账单，不报成功 |
| `6001` | 取消 | 提示未完成 |
| `6002` | 网络错误 | 提示核对账单 |
| `4000 / 5000` | 失败或重复请求 | 提示未完成 |

debug 日志 tag 为 `SmartLife798/Evidence`；release 中 `Diag` 不输出业务日志。仅保留状态摘要，例如：

```text
prepay.ok billId=... payType=21 orderBytes=...
alipay.result resultStatus=9000
alipay.outcome billId=... success=true resultStatus=9000
confirm.ok billId=...
dev.start.accepted did=... ptype=21 dtype=6 hasData=false
dev.start.confirmed did=... state=启动中
dev.end.ok did=...
dev.start.fail did=... ptype=... code=-52
```

其他服务端消息日志仍需按用例审查，不能由 SDK 白名单整改推断全部日志均已脱敏。

### 服务端启停

| code | 已核实语义 | 客户端处理 |
|---|---|---|
| 非负 | 命令受理 | 状态确认后才报启动/结束；不证明结算 |
| `-2` | 该类水控器仍运行，要求机身结算 | 保留查询入口，按机身提示操作 |
| `-52 / -88` | 未付账单或需先支付 | 拉取未付账单并引导支付面板 |
| `-87` | 余额不足 | 提示余额不足，不自动扣款 |
| `-99` | 登录过期 | 统一清会话 |

命令信封的 `data` 非固定对象：原 Retrofit 声明为 `BaseReq<Object>`，客户端将信封与载荷分开解析，接受字符串/数字/数组/对象/null。旧 `ApiResp<Unit>` 对 `data:""` 的解析缺陷已有单测修复；热水机真实载荷形状尚缺抓包复核。

### 计费字段

账单关键字段为 `id / ctime / utime / payment / discount / status / type / cata / dir / msg / dev / prds`。`status=3` 已付款、`1/4` 未付/失败、`2` 待确认、`5` 核算中、`9` 取消。账单、金额与执行结果以服务端为准；本机计时不是计费依据。

## 3. 实测步骤

### 3.1 支付宝

用户授权后选已有待付账单 → 订单页去支付 → 渠道/预支付 → 有订单串才交 SDK → `trans/confirm` → 核对服务端账单。取消、超时、受理和 SDK 成功都不能单独证明实付。

使用 debug 包按需抓 `adb -s <目标序列号> logcat -d -s SmartLife798/Evidence`，仅保存白名单状态与脱敏摘要；不原样导出签名回执。

### 3.2 设备 start/end

用户具体授权与现场条件具备后，按详情状态单次启动，分别观察受理与确认；结束同样区分 `dev.end.accepted` 和同设备待机后的 `dev.end.ok`。随后核对账单、设备归属和实际出水/结算；不自动重发命令。当前确认实现见 [docs/03](03-技术方案与开发计划.md#31-全自动刷新无手动刷新按钮)。

## 5. 启动链路实测（2026-10-21，真实账号）

饮水机尾号 **7339**，dtype=5、康之源 SK-450-1、ntype=9；`payItems=[91,21]`、钱包为 0，企业 `dmode=1 / emode=41`。厂商二维码 `https://i.hnkzy.com/q/1/<设备编号>` 被 `qr/use` 解析为 `type=3` 和同设备。

| 操作 | 历史观察 |
|---|---|
| `dev/start?rcp=true&ptype=91` | code=0，返回 302 位设备帧；连续 6 次 gene.status=99，未执行 |
| `dev/start?rcp=false&ptype=91` | code=0、data 为空；2s 内 gene.status=1 |
| 客户端 1.2.6 扫码/手输后启动 | 捕获 accepted/confirmed；首页显示启动中与已授权取水 |
| 未按机身启动即调用 end | code=-2 要求机身结算；后续回到 99，生成 status=3、payment=0.0 的账单 |

结论仅支持该类水控器的 `rcp=false` 执行规则与「App 授权 → 机身启动/结算」流程，不能证明物理出水或非零计费。

同次 `bill/pay/channels` 返回支付宝渠道；对已付账单调用 `prepay/21` 被以「账单状态已改变」拒绝。无待付账单，未完成真实支付宝扣款；该企业记账模式下的 0.00 自动结算不等于实付。

| VersionCode / User-Agent | 历史结果 |
|---|---|
| 3.1.5 / Android_ilife798_3.1.5 | 详情 code=0；启动 code=-1「请升级最新版APP」 |
| 3.1.7 / Android_ilife798_3.1.7 | 启动 code=0，状态 99→1；结束受理后回到 99 |

#### 详情过渡与 NFC 自动开始（2026-10-29）
