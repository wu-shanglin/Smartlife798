## 2. 工程结构

依赖方向为 `MainActivity / ui → MainViewModel → core → 服务端`，共享状态经 `StateFlow` 返回。`core` 负责 HTTP/解析、状态机、命令参数、支付桥与 Store；VM 负责编排、账号与演示隔离；UI 负责生命周期内的展示和回调导航。模块责任表与存储分类见 [docs/06](06-工程规范与路线图.md#1-代码与数据责任)。

Compose、导航、SDK 依赖以 Gradle 真值为准，不因文档维护升级。Compose 1.10.6 的选型依据为 [稳定共享过渡 API](https://developer.android.com/jetpack/androidx/releases/compose-animation#1.10.0) 与 [布局坐标缓存优化](https://developer.android.com/jetpack/androidx/releases/compose-ui#1.10.0-beta01)；不据此宣称当前设备帧率已达标。共享过渡使用现有 `SharedTransitionLayout`、`sharedBounds` / `sharedElement`；匹配键包含来源条目、入口、设备与内容，导航刷新等待目标 RESUMED 和过渡稳定后再执行；详情响应立即发布，最终视口与独立绘制层隔离共享容器几何，以图层缩放替代动画约束重测量，不等待动画完成。UI 行为及官方选型链接统一见 [卡片过渡与返回手势](02-功能设计与UI方案.md#66-卡片过渡与返回手势)。

## 3. 关键机制

账单和支付面板共用 `AppBottomSheet`：使用当前窗口尺寸确定内容视口，保留 ModalBottomSheet 的完整父约束供框架计算展开/隐藏锚点；手柄与底部/水平安全区放在有限视口内部，移除随面板偏移变化的顶部安全区测量反馈。不要将 `fillMaxHeight` 直接加在面板 Surface 上，否则框架会误把缩小后的高度当成完整窗口。明细使用剩余空间滚动，标题和操作区固定，详情 hide 完成才切换支付。`ExpressiveControls` 复用官方 ButtonGroup 的相邻宽度联动与下拉刷新形变，语义色由主题提供，业务请求仍由 VM 编排。

账号资料使用单字段 `ProfilePatch`，省略无关字段；昵称和积分设置共享入口互斥，设备命令期间不能修改，保存期间不能启动。服务端成功才写共享状态与账号缓存，版本戳拒绝保存前发起的旧 master 响应；切换账号/演示取消任务并拒绝旧响应。头像由 VM 调用 `Avatar`：独立无鉴权 HTTPS client，不重定向、不自动重试，限制 2 MiB 与解码尺寸，在 IO 下载/解码，可取消；UI 只显示结果及首字占位。

签到由 VM 管理登录与前台任务，自动开关为安装偏好、默认开启；手动按钮不依赖自动开关，始终先读最新状态。两入口共用互斥，自动可取消地等待旧 VM 清理后再检查；手动处理中不重复提交。依据 `mission-lst` 信封时间及中国时区计算当天/星期；已有积分账号的 daily/week 缺失按原版零值准备请求，非法位图或缺账号/时间/奖励仍拒绝。

提交前原子落盘当天尝试记录，防止多 VM 或进程重建重复写入；落盘后再次核对日期并以服务端时间加单调时钟间隔生成摘要，跨午夜不提交旧日期请求。资料/签到请求使用一次性正文，关闭连接重试与重定向，防止 HTTP 503 等内部重发；API 可取消等待将协程取消传至网络 Call，已调用提交的当天记录仍保留。受理后查询确认，再刷新真实积分余额；未知、失败及超时不自动重新提交，手动先查后可明确重试；复用当天标记也必须重新确认 commit 成功，避免内存值存在而盘面写入失败。已知未提交的取消仅清除本次新建标记，不能删掉旧的不明请求记录。

成功、失败原因及待确认状态发往全局提示，自动相同结果去重；手动每次反馈，提示按导航实际高度避让。请求绑定发起时令牌，迟到或排队的旧令牌拒绝事件不能注销新会话；登录响应也绑定发起时的会话代次，进入或退出演示后不接受迟到登录成功。退出入口立即取消账号任务并清本地会话，远端退出固定使用旧令牌，迟到结果不改新会话。退出演示不联网、不写存储；后续真实登录成功时核对 Store.uid，仅已确认同 UID 才继承缓存，其他归属清账号数据但保留安装偏好。原 APK 与独立摘要的依据及边界见 docs/01、docs/04。

ButtonGroup 外层占满行宽、内部放松最小宽度：当前 Material3 alpha14 的溢出测量仅缩小 maxWidth，若仍收到整行的 minWidth，会在小屏/大字体时产生非法约束。保持有限的最大宽度和原生溢出菜单，不升级整套依赖或自行复制框架测量逻辑。

### 3.1 全自动刷新（无手动刷新按钮）

| 触发 | 实现 |
|---|---|
| 打开应用 / 从后台回到前台 | `LifecycleResumeEffect` → `vm.bumpRefresh()` |
| 进入任一页面 / 返回上一页 | `currentBackStackEntryFlow` 等待目标 RESUMED 与共享过渡结束 → `vm.bumpRefresh()`（200ms 合并） |
| 页面响应 | 除设备详情外使用 `LaunchedEffect(refreshTick) { load() }`，首帧也会执行 |
| 设备详情 | `collectRefreshRequests` 首次立即加载，加载期间合并信号，不取消重启；启动中/运行中每 2s 轮询 `dev/status`（含启动成功后 20s 受限窗口），空闲与异常状态不轮询，仅页面 RESUMED 时运行。`StartCommandLock` 最多 20s，仅在待机、有本设备记录、未见运行态时保护重复启动，状态变化立即解锁；请求忙碌态没有固定冷却 |
| 首页 | `refreshAll()` → `master` + 钱包 + 由账单派生的历史 + 进行中记录对账（`dev/status`） |
| 我的 / 设备 | 我的独立 `refreshMaster()` + `refreshWallet()`；设备 `refreshMaster()`；下拉均调用 `refreshAll()` |

#### 启动确认（`dev/start` 之后）

`code >= 0` 只代表服务端受理。以下为客户端状态处理；原命令参数和设备状态依据见 [docs/01](01-逆向分析报告.md#7-设备使用流程热水机--淋浴机)。

| 步骤 | 说明 |
|---|---|
| 1 | 启停共用 VM 互斥；`dev/start`（`did/upgrade/ptype/args/rcp=false/cnt`）受理后先保存独立 `pendingStart` 书签；确认任务归属 VM，返回首页不取消，登出/演示切换取消旧账号任务 |
| 2 | 首读前等待 1s，随后间隔 2s，最多读取 5 次；次数与等待值以 `StartWatch` 为准（网络耗时另计）；快照是残缺对象；先检查同 id 且包含在线状态及业务状态，再合并到已知设备（`mergeStatus`）判定，空/异设备/缺字段响应保持未知 |
| 3 | 设备进入 `1/30/10/20`（开机/准备中/运行中/冲洗中）→ 将待确认书签提升为「进行中」并清理待确认；本机计时起点保留受理时间，不等于服务端计费起点 |
| 4 | 一直 `99`（待机）或离线/故障 → 返回 `START_UNCONFIRMED` 并清待确认；状态读取失败/缺失 → 同样不报成功，但保留待确认供后续刷新/重建恢复；不自动重发启动 |
| 5 | 未确认时不再伪造「使用中」：首页/订单卡片的胶囊只来自服务端快照，首帧显示「同步中」；`refreshAll()` 与回前台会用 `dev/status` 对账本机记录 |
| 范围 | 第 2–4 步只对状态可观测的设备族生效（`StartWatch.isObservable`：水控/淋浴/饮水机、洗衣/烘干/洗鞋、吹风机、充电桩）。消费机/售货机/门禁可能在 `99` 下就能用，仍按「服务端受理」记录，避免误报失败 |
| 结束 | 机身仍在运行时 `dev/end` 返回 `-2`「请在设备上点击结算」；客户端保留记录并提示，等设备回到 `99` 再清除 |
| 状态模型 | `dev/status` 按 `StatusSnapshot`/`DeviceStatus`（局部）建模，`Api.deviceStatus` 返回局部状态而非完整 `DeviceDetail`；详情页走 `pollDevice(did, base)`、其余路径各自持有已知设备，统一经 `Device.mergeStatus` 合并 |
| 类型缺失 | 账单/收藏/最近等可能拿到局部设备的地方，类型标签用 `DeviceType.nameOrNull()` 回退「设备/—」，不用会得到「智能设备」的 `name()` |

#### 进行中轮询（首页“使用中”卡片 / 订单“使用中”分栏）

| 项 | 说明 |
|---|---|
| 触发 | 本机存在「进行中的使用」或待确认书签，且 App 处于前台；命令确认期间由命令独占读状态 |
| 周期 | 每 **2s** 调一次 `GET /ui/app/dev/status?did=&more=false`（实际间隔 = 请求耗时 + 2s） |
| 展示 | 卡片状态胶囊取服务端 `gene.status`（运行中 / 冲洗中 / 启动中 / 离线 / 禁用…），并显示「服务端 HH:mm:ss」；没有快照时显示「同步中」，不显示「使用中」 |
| 结束判定 | 只以同设备完整状态的待机/异常清除书签；未知、空/异设备/缺字段响应不清除。详情、全局轮询与刷新复用同一对账函数，命令前迟到响应按修订号丢弃，账号变化按令牌丢弃 |
| 对账 | 每次 `refreshAll()`、回前台与启动时各补一次 `dev/status`：待机/异常即清除本机记录，不等轮询循环 |
| 让位 | 打开该设备详情页时暂停（详情页自己 2s 轮询并回传 VM）；异步首载、运行态和命令忙碌变化重新评估详情轮询，避免首载时无设备导致循环退出后不再启动 |
| 后台 | `onPause` 取消任务、不再发请求；回前台立即补一次再继续 |
| 边界 | 不驻留后台、不起 Service、不申请额外权限；预览模式不轮询 |
刷新是**静默**的：已有数据时不显示整页 Loading，只在首次进入显示；这样返回页面不会闪白。

详情页用 `collectRefreshRequests` 在页面创建时立即加载，与进场并行；完整结果立即展示，不再等待共享过渡完成。加载期间合并 `refreshTick`，不因导航结束后的 200ms 刷新信号取消首个请求再重发；后续信号仍刷新，页面移除时取消收集与请求。不持久缓存完整详情，不改变启停与支付的服务端确认依据。

页面与根布局的 Flow 使用 `collectAsStateWithLifecycle()`，生命周期停止时暂停 UI 收集。首页/订单的进行中用时由独立 `UsageDuration` 文本每秒更新，仅在目标页面 RESUMED 时计时，避免计时触发整页重组，返回后按当前时间补齐。首页排序与设备页关联使用按 id 的索引；过滤和类型集合按数据/筛选条件缓存，搜索输入只重算过滤结果。下拉刷新入口防重复并在 `finally` 释放指示状态，主数据加载也在取消时释放状态，丢弃账号变化或进入演示前发出的旧主数据响应。这些改动不改变服务端计费、设备状态和命令确认规则；真机帧率与耗电改善仍需实测。

#### 结束确认

启停共用 VM 互斥。结束非负码只表示受理；`EndCommand` 最多读取 6 次同设备状态，首次立即、后续间隔 2s，确认在线待机后才清记录。空/异设备/缺少待机证据的状态、异常或持续运行不能报成功；未确认保留入口，不自动重发。详情直接采用确认快照，丢弃命令前的迟到读取，避免被滞后全量详情覆盖；账单仍以服务端结算为准。

### 3.2 历史数据来自云端

原应用没有本地"最近设备"表。最接近的云端数据是**账单历史**（每条 `BillData` 都带 `dev`）：

```
GET /api/v1/bill/lst-owner?page=0&size=50   # 服务端 page 从 0 开始
  → 按 bill.dev.id 聚合：次数、最近时间、设备快照
  → 与"仅扫码未使用"的设备（本地）合并
  → 写入本地索引，供首页"常用设备/最近使用"、设备页"常用/最近"排序
```

> 分页基准：UI 第 1 页必须传 `page=0`，传 1 会被服务端当成第二页而返回空列表。

收藏本身完全由服务端下发（`master.favos`），本地只缓存快照做首屏。

### 3.3 手动输入编号

「手动输入」是独立页面：输入设备贴纸编号或二维码里的 `id`，走与扫码完全相同的链路：

```
QrParser.parse(text) → GET /api/v1/qr/use?id=<id> → 按 QrFlow 校验 qr.type / dev → 设备详情
```

纯数字按原应用规则识别为"编号/充值卡"类型，但最终是否进入设备页由服务端 `qr.type` 与 `dev` 决定：明确的非设备类型拒绝，缺类型但有可用设备时按设备处理。

### 3.4 支付宝支付

与原客户端相同的三段式：

```
GET /api/v1/bill/pay/channels?id=<billId>        // 可用渠道
GET /api/v1/trans/prepay/21?id=<billId>          // data 可为空（免密），或为签名订单串
PayTask(activity).payV2(orderInfo, true)          // 仅有订单串时拉起 SDK
GET /api/v1/trans/confirm?id=<billId>             // 服务端确认
```

**关于"逆向原 APK 的签名"**：支付宝 APP 支付**不使用 APK 签名**。安全链条是——

1. 服务端用**商户私钥**对 `orderInfo` 签名（`app_id`、`biz_content`、`sign`）；
2. 客户端只把这个字符串交给支付宝 SDK，SDK 与支付宝 App 校验商户签名；
3. 支付结果再由服务端 `trans/confirm` 反向确认。

因此"复用原 APK 签名"既无必要也不可行；正确做法就是集成官方 SDK 并复用服务端下发的订单串，本项目即按此实现。余额/钱包（`91/92/93`）无需 SDK，服务端直接扣款；微信 SDK 已集成，仍需包名/签名/appId 匹配；云闪付/银行 SDK 未集成。签约使用协议类型 20 的 `sign`，不是支付渠道 21，也不从 `acc-pgas` 推断签约状态。

### 3.5 错误与令牌

`code=-99` → 清会话 → 登录页 + Snackbar；`-87/-88/-52/-28` → 引导充值/支付；网络读取失败 → 内联错误与刷新入口；启停、支付等副作用请求不自动重试。

## 4. 构建与运行

Python 3.10+、Git；Android 工程需 JDK 17+（CI 使用 21）、SDK Platform 36 与当前 Gradle 所需 Build Tools。依赖版本见本页技术选型和 Gradle；不要将本机 JDK 路径写进受控配置。

1. 本机设置 `JAVA_HOME`；在忽略的 `SmartLife798/local.properties` 中设置 `sdk.dir`。
2. 在仓库根目录按 [检查与证据](06-工程规范与路线图.md#2-检查与证据) 运行根目录检查与适用 Gradle 任务。
3. 先核对目标设备，再安装；演示入口不使用业务账号：

```powershell
adb -s <目标序列号> install -r SmartLife798/app/build/outputs/apk/debug/app-debug.apk
adb -s <目标序列号> shell am start -n com.smartlife798.app/.MainActivity --ez preview true
adb -s <目标序列号> logcat -s SmartLife798/Evidence
```

`local.properties`、`keystore.properties` 和签名材料均不入库。release 签名、构建产物、版本准备与发布步骤统一见 [版本与发布](06-工程规范与路线图.md#3-版本与发布)。
