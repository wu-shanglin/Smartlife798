| 品牌 | 应用名 **慧生活798**；自述"用于日常生活如直饮水、热水淋浴、互联网洗衣、电吹风等的服务性软件" |
| 技术形态 | 原生 Android（Kotlin + Java），ARouter 多模块 + Koin 依赖注入 + MVVM + Retrofit/OkHttp + Gson；非 uni-app/H5 壳 |

| 业务边界 | 热水机、直饮水机、淋浴机、洗衣机、吹风机等设备共用同一套"设备详情 / 启停 / 计费 / 账单"模型 |
| 收藏 | **服务端能力**（`/api/v1/dev/favo`，收藏列表随 `/api/v1/ui/app/master` 下发） |
| 常用/最近 | 原应用**没有**本地常用设备/最近使用机制，仅有内存缓存；需要新增（本地库） |

**一句话**：这套 App 的核心并不是"扫码后本地开设备"，而是"扫码 → 服务端解析二维码 → 服务端下发设备与计费规则 → 客户端调用服务端启停接口 → 服务端结算生成账单"。因此新客户端必须对接 `i.ilife798.com`，UI 可以完全重做。

### 4.3 响应信封

`coremodel/data/req/BaseReq.java`、`coremodel/data/bean/HttpResult.java`、`datasource/a.java`：

```json
{ "code": 0, "msg": "…", "data": { }, "size": 0, "time": 1792512371043 }
```

- `code >= 0` → 成功（`0` 表示无附加业务码）
- `code < 0` → 失败；`msg` 直接面向用户展示
- `code == -99` → **令牌失效**，原客户端会广播"签名验签失败，请重新登录"事件并跳登录（`CoroutineHttp.handleResponseX` / `datasource.a.M1`）
- HTTP 非 2xx → `ApiError`，客户端提示"服务器开小差了，请稍后重试"

### 4.5 请求签名

- 登录、设备、账单等现有普通接口原样透传 `Authorization`；`BaseParm` 仅含可选 `token`，不能据此推断全部接口都没有额外摘要。
- `-99` 的令牌错误仍按统一会话失效处理。积分签到另有 `score-send?sign=&s=1` 的业务摘要，3.1.10 已改为 `BaseTaskFragment.U()` → `OctUtil.d/e()` → `liboct` 的 native `s()`，详见 §5.4。
- 原 JNI 先校验运行应用的证书，失败返回空摘要。用户已明确授权在合法登录会话和自研包名/签名下独立重实现摘要；本项目不携带原版 `.so`、不伪造官方证书、不复用其签名私钥，也不绕过服务端登录鉴权。离线重实现不等于已获服务端兼容性或真实签到验收。

登录流程（`module/login/view/activity/LoginActivity.java:200-444`）：

1. 进入页面即生成 `seed = Random.nextDouble(0,1)`，请求 `/api/v1/captcha/?s=<seed>&r=<now>` 显示图形码；
2. 填手机号 + 图形码 → `POST /api/v1/acc/login/code`（body 里的 `s` 就是同一个 seed）；
3. 填短信码 → `POST /api/v1/acc/login`（`un`+`authCode`，`openCode` 仅支付宝快登时使用）；
4. 成功 → `App.C(LoginData)`：持久化登录数据、把 `token` 写入 OkHttp 头；
5. 若返回 `-98`，切换到支付宝登录页，用返回体里的 `oid` 继续。

`common/util/q.java`（`QrUtil.B`），原客户端**先本地正则识别，再交服务端 `qr/use` 确认**：

| 正则（摘要） | 本地类型 | 取 id 方式 |
|---|---|---|
| `^\d+$` | 1 | 整串数字 |
| `https://…/q/<n>/b?id=<id>` | 2 | `?id=` 之后 |
| `https://…/q/<n>/s?id=<id>` | 3 | `?id=` 之后 |
| `https://…/q/<n>/billing?id=<id>` | 5 | `?id=` 之后 |
| `https://…/q/<n>/vip?id=<id>` | 6 | `?id=` 之后 |
| `https://…/q/<n>/wallet?id=<id>` | 7 | `?id=` 之后 |
| `https://…/q/<n>/bm?/<code>` | 8 | `q/1/` 之后 |
| `https://…/q/<n>/<token>` | 4 | 最后一段 |
| 其它 | -1 | 原文 |

随后 `MainActivity.I0()` 把 `(type,id)` 交给 `DeviceVM.E(id)` → `GET /api/v1/qr/use?id=<id>`，再按**服务端返回的 `qr.type`** 分流（`QRCodeType`）：

| type | 含义 | 原应用行为 |
|---|---|---|
| 1 | 充值卡 | 打开充值页 |
| 2 | IC 卡 | 打开绑卡页 |
| **3** | **设备** | **按设备类型进入详情（本项目核心）** |
| 4 | 消费券 | 领券 |
| 5 | 云袋 | 打开云袋详情 |
| 6 | 洗衣洗鞋 | 打开洗衣业务 |
| 7 | 账单/VIP | 按前缀进账单/钱包/VIP |
| **8** | **门锁** | **进入门锁详情** |
| -1 | 未知 | 提示无法识别 |

> **实机二维码（2026-10-21 解码）**：康之泉饮水机面板上的码是
> `https://i.hnkzy.com/q/1/861089059737339`，和官方 App 生成的
> `https://i.ilife798.com/q/1/b?id=<id>` 不同：域名是厂商域（同样解析到 11.18.x.x 的后端），
> 路径也没有 `b?id=`。按上表它落在「通用」分支（本地类型 4，id = 最后一段），
> 真正的类型仍由服务端 `qr/use` 返回的 `qr.type` 决定。本客户端因此把
> 「服务端没给 `qr.type` 但给了 `dev`」也当作设备码（原应用只认 3/8），
> 否则这类厂商码会在服务端已解析出设备后被本地判成「消费券」。

热水机（`dtype=5` 直饮水）、淋浴机（`dtype=6`）、饮水机（`dtype=8`）、洗衣机（`dtype=10`）走的都是这条通用链路。

### NFC 设备卡片入口（2026-10-28）

用户提供的卡片经一加手机前台 reader mode 读取，系统缓存包含 NFC-A / NDEF，两个 NDEF 记录分别为 URI 与 Android AAR。URI 外层为 `https://render.alipay.com/p/s/ulink/xty`，查询键为 `s`、`scheme`；AAR 包名为 `com.eg.android.AlipayGphone`。这解释了普通碰卡会交给支付宝的现象，但不能仅凭外层链接确定设备编号。

补采确认外层 `s=dc`，内层为 `alipay://nfc/app?id=20002153&t=<公开路由短码>`；`id=20002153` 是支付宝入口，不能误作慧生活设备 ID。初版按前缀过滤短码导致记录信息不足，后续已按用户要求改为开发者工具保存原始 NDEF（仅主动前台、本机有界日志，不自动跟随链接）。工具本身不注册后台 NFC 分发，不调用 `qr/use`、启停或支付；实际卡片的短码到设备映射仍需单独确认，不能以采集成功替代路由验收。

---

官方直接 NFC 卡片另有明确语法：3.1.10 Manifest 注册五个 HTTPS 域名（`i.ilife798.com`、`i.hnkzy.com`、`act.hnkzy.com`、`act2.hnkzy.com`、`prerelease.ilife798.com`）的 `/nfc.html`。3.1.5 / 31005 未加固样本经 REA 核对，写卡方法 `NfcReadWriteActivity.m0` 使用 `/nfc.html?q=<qrCode>`，`NfcActivity.k0` 取 `q`，随后经 `DeviceVM.E` 调用 `qr/use`；`q` 是二维码标识，不是设备 ID。3.1.10 的核心方法为 native，恢复 DEX 中的 nop 不能当作同版本方法实现证据。本次仅接入上述经过核实的链接形状与现有服务端设备解析，不扩展任意 schema。

进一步核对支付宝已安装 APK 的 DEX：该入口先改写到扫描应用并携带 `__near_field_source__=nfc`，默认路径由 NFCCoreService 转交 `NfcRouteRpcService.doNfcRoute`（`com.alipay.smartcode.nfc.route`），返回的 `routeInfo` 才可能包含后续设备入口。默认请求链需要客户端签名；不复用支付宝账号凭据或伪造签名。未携带凭据的公开请求仅返回平台错误，不能据此断言所有部署都禁止匿名解析。

另核对旧扫码回退 `alipay.mobilecodec.route`：使用正确的 `paiType=qrCode` 和 `decodeData.code` 后可得到业务成功，但结果是 `actionType=copyOnly` 的通用文本页面，没有设备 URL 或设备 ID，不能作为设备映射成功。当前缺口是获得有效的 NFC `routeInfo` 或供应商公开映射接口；不将卡片短码直接当设备编号，也不以手动绑定替代用户要求的自动识别。

`apply=6` 是原客户端固定值（两个入口都传 6），服务端语义未公开 `[推断]`：可能表示"详情页所需的数据集合"。

| 字段 | 类型 | 用途 |
|---|---|---|
| `device` | `DeviceInfo` | 设备主体：`id/name/status/ntype/gtype/btype/fmv/memo/bm/gene/ep/addr/subs/gs/ext/ls` |
| `deviceShare` | `DeviceShare` | **非空 = 已收藏**（含 `id/ctime`） |

### 7.2 设备状态模型

- 网络态：`DeviceInfo.status`：`0` 离线 / `1` 在线（`NetworkStatus`）。
- 业务态：`DeviceInfo.gene.status`（`DeviceStatus`）：`0` 关闭、`1` 开机、`2` 异常、**`10` 运行中**、`20` 冲水中、`30` 准备中、`99` 锁定/待机（客户端展示为"在线"）、`98` 强制禁用。
- 当前模式：`gene.mode`（`DeviceMode`：`11-14` 洗衣机、`81-84` 烘干机、`91-94` 洗鞋机、`101` 取件、`62` 消费机登录…）。
- 通道/仓位：`gene.pos` / `gene.out`；多通道设备用 `DeviceInfo.subs[]`。
- 客户端把状态映射为中文标签（`q.g`）：`蓝牙 / 离线 / 在线 / 禁用 / 启动中 / 运行中`，颜色分别为灰/灰/蓝/红/红/黄。
- 本客户端按同一决策表实现（`core/DeviceTypes.kt`），并补上原应用的关键细节：**热水机/直饮水机只在 `99`（锁定/待机）时提供「立即使用」**；`1`（开机）、`30`（准备中）、`10`（运行中）、`20`（冲水中）都属于"已启动"，主按钮必须是「结束使用并结算」，否则会在设备准备期间重复提交 `dev/start`，被服务端以「设备准备中，请稍后再试」拒绝。`2`（异常）与 `98` 仍是不可用状态。

### 7.3 轮询

`DeviceCommonDetailActivity.b2()`：若当前标签为"运行中/启动中"，则执行 `P1()`（广告+`startPolling`）与 `V1()`；`V1()` 通过 `postDelayed(...)` 延迟再次请求状态。`BaseDeviceDetailActivity.U0()` → `DeviceVM.k(did,false)` → `GET /api/v1/ui/app/dev/status?did=&more=false`。

轮询周期来自被混淆常量（`com.igexin.push.config.c` 字段），无法静态还原精确毫秒值 `[推断]`。本客户端的 2s 轮询、启动待确认恢复、账号/命令守卫和状态锁是实现策略，统一见 [docs/03](03-技术方案与开发计划.md#31-全自动刷新无手动刷新按钮)，不能反推为原应用或服务端承诺。

> **`dev/status` 的 `device` 是残缺对象**：只有 `id/status/gene/subs/ext`，**没有 `bm`**（因此也没有
> `dtype`），`name` 也是空串。状态映射依赖 `bm.dtype`（水控机的 `1/30/10/20` 才映射为
> 「启动中/运行中」），所以客户端必须把快照合并到已知设备上，否则 `gene.status=1` 会被当成
> 「在线」，进而把正在出水的会话判成已结束。
>
> 本客户端在类型层做了隔离：`Api.deviceStatus()` 返回 `StatusSnapshot`（内含 `DeviceStatus`），
> 它**不是** `Device`，因此「把状态快照当成完整设备渲染」在编译期就写不出来。渲染/判定前必须
> `device.mergeStatus(snapshot.device)`；反向由 `Device.statusOnly()` 投影。`dtype` 未知时
> 用 `DeviceType.nameOrNull()` 渲染「设备/—」，不要用 `name()`（会得到「智能设备」）。

### 7.4 启动 / 结束

`BaseDeviceDetailActivity.T0()`（启动）：

```
GET /api/v1/dev/start
  did     = 设备 id
  upgrade = true
  ptype   = 选中的支付方式（DeviceCacheData.payType，默认 0）
  args    = 业务参数（JSON 字符串，见下）
  rcp     = false
  cnt     = 1 或 2（由本地缓存开关决定，见 q.y()）
```

> **`rcp` 是 `false`，不是 `true`**。`l4.a.C1347a` 的默认参数是 `false`，`T0(..., Boolean.TRUE, ...)`
> 里的 `TRUE` 是 `upgrade`。2026-10-21 用真实饮水机验证：`rcp=true` 时 `dev/start` 的 `data`
> 返回 302 位设备帧、`gene.status` 一直 `99`（机器不动作）；改成 `rcp=false` 后 `data` 为空，
> 2 秒内 `gene.status` 变成 `1`。`rcp` 语义是「回执」——要回执就不下发执行。

`BaseDeviceDetailActivity.Q0()`（结束）：

```
GET /api/v1/dev/end?did=<did>&rcp=false
```

> 机器仍在运行时 `dev/end` 会返回 `code=-2`「设备运行中,请在设备上点击结算」；这类水控器
> 必须在机身上按「结算」结束，客户端不应把它当成普通失败。

本客户端受理结束后继续确认同设备在线待机；空/异设备/异常快照不能证明结束或结算成功，不自动重发命令。实现与页面反馈分别见 [docs/03](03-技术方案与开发计划.md#31-全自动刷新无手动刷新按钮)、[docs/02](02-功能设计与UI方案.md#44-设备详情)。

**支付渠道**（`e0.java` 的 `PayTypeInfo`）：91 钱包支付、21 支付宝免密支付、41 银联免密、
93 一卡通、52 农行免密。这里的「免密」是**签约后服务端直接扣款**：客户端只调
`trans/prepay/{type}?id=<billId>` 再 `trans/confirm?id=<billId>`，只有服务端返回订单串
（未签约）时才需要拉起对应 SDK。`prepay` 在已签约时返回空 `data`。

**微信支付**（`PayHelper.java:225-240`）：`GET /trans/prepay/11?id=<billId>` 返回
`{appid, partnerid, prepayid, noncestr, timestamp, package, sign}` 七元组，客户端填进
`PayReq` 调 `IWXAPI.sendReq`；`appid` 为空时原版回退硬编码 `wx03092553dbf49755`。回调入口必须是 `{applicationId}.wxapi.WXPayEntryActivity`
（`IWXAPIEventHandler.onResp`），结果码再交给 `trans/confirm` 定论。
微信会校验「包名 + 应用签名 + appId」在开放平台登记一致，换签名/换包名都会得到 `errCode=-1`。
**支付宝免密签约**（`AgencyDialog.N` → `PayHelper.z(258)` → `PayTask.payV2`）：

```text
GET /api/v1/ui/app/sign-pga?type=20     # 协议类型 20 = PGAgreementType.ALIPAY（21 是支付渠道）
PayTask.payV2(data.sign, true)          # data.sign 是协议页的授权参数，真正打开支付宝签约页
```

`data.code`（pgacode）只在积分广告开关打开时由 `h0()` 拼成
`alipays://platformapi/startapp?appId=2019061465519660&page=/task/pouch&query=pgacode=<code>`，
属于「小荷包」入口，不是主签约路径。`acc-pgas` 返回的是协议渠道集合（`type=20` 支付宝），
不能用来判断当前用户是否已签约。

签约完成后 `trans/prepay/21` 才返回空订单并由服务端直接扣款；未签约时返回支付宝订单串走 SDK。
**钱包与充值**（`RechargeActivity` / `BillViewModel`）：

```text
GET  /api/v1/acc/wallet/owner                 # data.aw 是钱包，data.eps 是企业钱包列表
GET  /api/v1/prd/lst?eid=&type=1&status=1&all=false&did=&page=0&size=100&hasCount=false
POST /api/v1/bill/save                        # body 见下，data = 新账单 id
```

`bill/save` 的 body（`RechargeBillParm`）：

```json
{
  "ep":      {"id": "<企业 id>", "cata": 1},
  "prds":    [{"id": "<商品 id>", "count": 1}],
  "owner":   {"id": "<登录用户 id>", "cata": 1},
  "contact": {"id": "<钱包 owner id>", "cata": 1},
  "cata":    1,
  "note":    "<商品名>"
}
```

金额由服务端按商品计算，客户端不上送价格；充值单创建后与普通账单一样走
`bill/pay/channels → prepay → confirm` 支付。

`args` 的构造（`DeviceCommonDetailActivity.o()` / `q.b()` / `q.j()`）：

| 场景 | args |
|---|---|
| 有模式、无货道 | `{"mode":<mode>}` |
| 有模式 + 货道（洗衣液等） | `{"mode":<mode>,"ext":[{"pos":0,"out":1}]}` |
| 有通道/仓位 | `{"pos":<pos>,"mode":<mode>}` |
| NFC 触碰启动 | `{"touch":1}` |
| 无模式设备 | 空串 |

启动结果处理（`DeviceCommonDetailActivity.j2`）：成功即刷新界面；失败按 §4.4 的错误码弹充值/支付/先享后付等引导。**计费、扣款、订单生成全部在服务端完成**，客户端只负责调用。
