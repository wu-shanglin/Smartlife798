开发约束以 [AGENTS.md](../AGENTS.md) 为准；本文维护存储分类、检查方法、发布流程、Git 提交规则与尚未完成的工作。

| `ui/` | 页面、组件、主题、展示格式化 |

### 存储分类

仅 `Store` 访问 SharedPreferences。新增键必须明确所属类别、退出登录行为及迁移方式；改字段不允许静默丢失进行中设备入口。

| 类别 | 当前键 | 登出/令牌失效 |
|---|---|---|
| 账号 | `token`、`uid`、`phone`、`profile`、`active`、`favcache`、`recents`、`pinned` | `clearAccount()` 删除；VM 同时清状态与账号任务 |
| 安装偏好 | `themeMode`、`dynamicColor` | 保留；`clearAll()` 才删除 |
| 安装级更新策略 | `updatePolicy`（已验证的公开 JSON） | 登出保留；无旧键迁移，缺失或非法视为未知；`clearAll()` 删除 |

演示模式不能修改以上任一类别。启动时恢复安装配置与演示运行期间的写入隔离要分别验证。

`check-repo.py` 使用 Git 跟踪文件和未忽略的新文件，检查：

- Markdown 相对链接的目标文件（不验证标题锚点）；`dist/` APK 未入库时允许缺失，由版本检查负责。
- core/vm 的反向依赖、UI 对 Api/HTTP/SharedPreferences 的直接使用（Api 常量展示允许；词法检查不能代替 Kotlin 编译或评审）。
- 禁止入库的产物、签名/本机配置，以及截图轮次名、源码快照、构建配置中的机器绝对路径。
- 未被当前文档引用的截图，避免重复残留。

它不扫描 Git 历史、不联网、不判断日志值是否敏感，也不能证明所有 VM 路径都有 Preview 与防重守卫。
连通性探针已迁入 `MainViewModel.checkConnection()`，统一演示、IO、会话变化与取消处理。UI 对 Api 的检查不保留文件哈希豁免；API 常量展示仍允许。

### 评审重点

- 服务端返回的未知/null/局部字段是否安全处理，状态快照是否同设备合并。
- VM 用例的 Preview、登录态、IO 调度、错误分支、取消与 `finally` 是否完整。
- 金额/启停入口是否防重；失败与超时是否保留可核对状态，避免自动重试扣款。
- 页面刷新 key、前后台轮询、相机资源、Sheet 切换与无障碍语义是否合理。
- 账号任务能否在登出后回写；日志是否仅含允许的状态码与脱敏摘要。
- 协议、文档、测试是否联动；交付是否区分本次验证、历史证据和外部待验。

## 3. 版本与发布

版本唯一真值：`SmartLife798/app/build.gradle.kts`。README、CHANGELOG、dist 与 tag 是发布副本。

| 版本位 | 触发条件 |
|---|---|
| MAJOR | 包名/登录/服务端协议或本地存储不兼容且无迁移 |
| MINOR | 新页面、新业务模块、外观等用户可感知的新能力 |
| PATCH | 缺陷、性能/稳定性、进入 APK 的依赖或工程调整 |
| 不发版 | 纯文档、CI、工具、截图整理；写入 Unreleased |

每次发布 `versionCode +1`，不复用、不回退；不从语义版本计算。一个 `versionName` 只能对应一份已发布内容。
不发布 alpha/beta/rc。验证中的 debug 构建不等于发布，不得将未验内容覆盖进 dist。

### 发布清单

1. 更新 Gradle 的 `versionName` / `versionCode`。
2. 将 CHANGELOG 的 Unreleased 提升为 `## [X.Y.Z] - YYYY-MM-DD`，日期用实际发布日期，顶部新建空 Unreleased。
3. 跑仓库检查、工具测试与完整 Gradle 检查；相关行为在设备上验收，限制写入 docs/05。
4. 将 APK 复制到 `dist/SmartLife798-X.Y.Z-debug.apk`，更新 README 的版本、产物链接及当前版本摘要。
5. 明确本次交付的 APK 路径；不要求删除旧版包，清理仅在确有需要且核对引用后进行。
6. `python tools/check-version.py --require-apk` 必须退出 0，确认版本信息一致且目标 APK 文件存在；普通 CI 不带该参数。
7. 验证通过后按默认 PR 流程提交并合入 `chore(release): X.Y.Z`；打 `vX.Y.Z` tag 和对外发布仍须用户明确要求。不得为填补历史缺失给当前 HEAD 补打旧版本 tag。

哈希仅用于更新包完整性、签名/原样本身份核对或明确的传输损坏排查；普通开发、文档、服务连通性检查与交付简报不要求逐项计算或附上哈希。

`check-version.py` 只精确核对 README 的当前版本和产物链接；`--require-apk` 额外检查目标 APK 文件存在，不读取 APK 内容、不校验哈希，也不限制旧版本文件共存。APK 内部版本、签名及更新元数据的一致性在实际发布或安装时核对。

release 签名配置位于 **Gradle 根目录** `SmartLife798/keystore.properties`；`storeFile` 相对该目录解析。
缺失时只能生成未签名 release。当前 R8 与资源压缩关闭，启用前须做 Gson 反射模型、扫码、启停与支付桥真机回归，不能仅凭 keep 文件存在认定可启用。

### GitHub 更新发布

仓库为 [wu-shanglin/Smartlife798](https://github.com/wu-shanglin/Smartlife798)。客户端读取最新正式 Release 的 `update.json` 附件；APK 地址固定为该仓库 `releases/download/v<versionName>/SmartLife798-<versionName>-debug.apk`，不接受远端任意 URL，不携带业务 token。附件直链规则依据 [GitHub 文档](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)。更新协议与官方业务服务端协议无关。

完成本节发布清单后，使用公开 UTF-8 说明文件和待发布 APK 生成元数据：

```powershell
python tools/make-update.py --min-supported-version-code 1 --notes <公开说明文件> --apk <已验证APK>
```

工具从 Gradle 读取版本并计算 APK 的 SHA-256，输出 `dist/update.json`。示例结构如下（示例值不是版本真值）：

```json
{
  "versionCode": 24,
  "versionName": "1.7.1",
  "minSupportedVersionCode": 23,
  "notes": "修复说明",
  "sha256": "待发布APK的64位小写十六进制SHA-256"
}
```

普通更新最低支持码维持既有支持范围（首次为 1）；需要强制所有旧版升级时设为本次 versionCode，仅淘汰部分版本时设为首个可继续使用的 versionCode。最低支持码必须在 1 与本次 versionCode 之间。先创建草稿并上传同名 APK、update.json，核对包名、内部版本、SHA-256 和现有安装签名，再发布 `v<versionName>`，设置为 latest；不能先发布强制策略再补 APK。更换签名不支持覆盖安装，禁止以卸载重装绕过校验，否则会丢账号和本机数据。当前交付使用 debug 签名，后续覆盖安装须保持同一签名；签名材料不入库。

#### 强制更新操作步骤

后续处理致命缺陷时，先修复、验证并准备新 APK，再配置此处策略。**没有单独的 `force=true` 开关**；实际条件为 `远端 versionCode > 已安装 versionCode` 且 `已安装 versionCode < minSupportedVersionCode`。只修改 CHANGELOG、Release 正文、仓库内某份 JSON 或官方 `Api.CLIENT_VERSION` 均不会开启强制更新；客户端读取的是 latest 正式 Release 的 `update.json` 附件。

以下假设待发布版本码为 24，仅用于解释范围，不代表当前版本：

| 发布目的 | `minSupportedVersionCode` | 已安装版本的行为 |
|---|---|---|
| 首次普通更新，仍支持所有已有版本 | `1` | 低于 24 的版本可稍后更新 |
| 仅淘汰 23 以下的版本 | `23` | 22 及以下强制；23 可稍后；24 无更新提示 |
| 强制所有低于本次发布的版本升级 | `24` | 23 及以下强制；24 无更新提示 |

后续普通发布要保留先前确定的最低支持码，**不能每次默认重置为 1**，否则会重新放行此前淘汰的版本。需要重新支持旧版时才有意降低门槛，并说明原因。大于本次 versionCode 的门槛无效，生成工具和客户端均拒绝。

1. 读取当前 Gradle 版本和线上 latest 策略，确认受影响版本范围；不要沿用本节示例数字或只比较 `versionName`。修复版的 `versionCode` 必须高于被淘汰的安装。
2. 按发布清单完成新版本构建、检查及覆盖安装验证。使用与现有用户安装一致的签名；CI 临时生成的 debug 签名不能直接替代现有发布签名。确认无须卸载、不丢本机数据。
3. 准备不含账号资料的 UTF-8 更新说明，明确缺陷影响和必须更新的原因。强制所有旧版升级时，在仓库根目录运行以下命令；版本值动态取自 Gradle：

   ```powershell
   $gradleText = Get-Content -Raw -Encoding UTF8 "SmartLife798/app/build.gradle.kts"
   $releaseCode = [int]([regex]::Match($gradleText, 'versionCode\s*=\s*(\d+)').Groups[1].Value)
   $releaseName = [regex]::Match($gradleText, 'versionName\s*=\s*"([^"]+)"').Groups[1].Value
   $releaseApk = "dist/SmartLife798-$releaseName-debug.apk"
   # 先准备此说明文件；evidence/ 不入库。
   $notesFile = "evidence/release-notes.txt"
   python tools/make-update.py --min-supported-version-code $releaseCode --notes $notesFile --apk $releaseApk
   ```

   仅淘汰部分旧版时，将参数值改成确认过的首个可继续使用版本码。工具生成 `dist/update.json`，自动填入新版本及 APK 哈希；不要手填哈希或使用另一个构建的 APK。

4. 获得本次发布授权后，在固定仓库创建 `v<versionName>` 草稿，将 `$releaseApk` 对应的同名 APK 和刚生成的 `update.json` 都上传为附件。核对 JSON 的版本码／名、最低支持码、SHA-256 与真实附件一致；不能只把 JSON 提交到 Git。
5. 发布草稿并设为 latest。核对公开 `https://github.com/wu-shanglin/Smartlife798/releases/latest/download/update.json` 返回本次策略，且 JSON 对应的固定 APK 地址可下载；两份附件必须同时可用。
6. 使用不含真实账号的低版本安装验证：自动／手动检查出现强制提示，返回和外部点击不能关闭；下载进度、取消／失败重试可用；取消系统安装仍受限；覆盖安装到达标版本后解除。若只淘汰部分版本，还要验证处于支持范围的旧版仍可稍后更新。最后记录真实安装版本与 APK 哈希，区分模拟器和真机结果。

**误配置恢复：** 修复 latest 附件 `update.json` 的最低支持码，并替换该附件；保持其版本及哈希与已发布 APK 一致。客户端联网重新检查有效策略后解除误拦截，手动「重新检查」可绕过 5 分钟间隔；离线缓存不会自行解除。若 APK 本身有缺陷，另发更高版本码的修复包，不用同一已发布版本覆盖内容，也不把 latest 指向无法满足门槛的更旧 APK。

纯策略调整不修改应用二进制，不需要仅为改最低支持码重建 APK，但仍需要对应发布／附件变更授权及上述范围验证。无更新功能的旧 APK、尚未取得新策略的离线客户端无法被这套客户端策略强制控制；它也不能绕过系统安装确认或替代服务端限制。

每次进入前台检查，自动间隔 5 分钟，手动绕过间隔，并发合并；下载中不更换策略。普通更新可在当前进程暂缓，手动仍可打开；强制提示不能用返回或外部点击关闭，移除业务页面，下载／取消安装均不解除。策略缓存跨登出与重启；网络失败保留已有策略，无有效缓存不新增拦截。误设强制策略时可替换 latest 的有效 update.json 降低最低支持码，客户端联网重新检查后解除，离线仍保留原限制。清数据可清策略，因此不等于服务端封禁。

安装包放应用私有 cache/updates，FileProvider 仅开放该子目录，以临时只读 URI 交系统安装器，不申请共享存储权限。下载最多 200 MiB、单次 5 分钟，读取超时 15 秒；不自动重试，取消删除半包。完整下载后及安装前均校验哈希、包名、版本名／码、当前签名；无法验证则删除／拒绝安装。进程退出后不续传，重新点击下载；正常下载完成后仅在前台打开安装流程。首次进入系统未知来源设置，用户授权返回后继续；系统安装必须由用户确认。相关平台行为依据 [Android PackageManager](https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls()) 与 [FileProvider](https://developer.android.com/reference/androidx/core/content/FileProvider)。

演示模式不联网、不写更新缓存、不下载、不拉起安装。首次部署须通知旧用户手动安装新版本；未集成此功能的旧 APK 无法被远程强制升级。系统安装、GitHub 可达性、不同厂商设置页分别验证；客户端无法保证无网用户及时收到此前未知的强制策略。

## 4. 文档与目录维护

Codex 随实现主动搜索受影响的文档与引用：README/使用说明、API 契约和数据结构、架构与模块职责、配置/环境变量/部署、用户流程与业务规则；实际引入数据库时才补结构与迁移说明。新增功能补说明，修改原位覆盖，删除功能清理过时描述。仅内部调整且不影响行为、配置或架构时，可不改说明文档；CHANGELOG 的 `Unreleased` 仍记录本次独立变更。完成时说明同步了什么或为何不涉及，不要求每次改遍所有文档。

- 当前事实只保留一个答案；README 只留当前版本摘要，历史在 CHANGELOG。
- 截图同名覆盖；清单记录真实/演示来源及版本限制。旧截图不能证明当前版本已回归；新截图使用演示数据并检查隐私。
- 删除前检查 Git 状态、全库引用、脚本输入与可再生性。目录递归删除前核对绝对路径在仓库内，不跟随链接，不运行 `git clean -fdx`。
- 原 APK、当前 dist、独有 evidence、签名和本机配置须保留。缓存、依赖检查副本与可再生逆向输出可按任务清理，不能仅因被忽略就删除。
- 反编译源码/DEX 元数据是静态依据缓存，可按 docs/01 重建；不进入版本库。下载工具保留一份可用安装，解压后重复压缩包可删除。
- 不把历史源码或生成的字段转储当作维护源码；只保留调用方实际需要、可追溯且有用途的文件。

| 中 | `Payment.kt` / `Api.kt` / VM 的宽泛 catch 与 `runCatching` | 协程取消按预期传播，支付回调等待可取消/超时且不误报失败后自动重试 |
| 中 | 真实支付、免密扣款、真机签约、微信平台配置 | 取得具体授权与真实条件，记录服务端 confirm、实际账单和 SDK 状态；目前未验 |
| 中 | 现场出水与非零计费闭环 | 设备物理按键配合，核对开始→取水→结算→账单；已有 0.00 账单不能代替 |
| 中 | 官方版本门禁与更新渠道持续核查 | 2026-10-23 已复现旧头可读详情但启动被拒；当前标识、签名样本及更新通道失真的排查见 docs/04。3.1.9 加固样本尚未完整恢复字段，不能把路径检测失败当通过；未来升级须重新核实原包与相关链路 |
| 低 | 字段级契约检测、R8、截图测试、TalkBack | 按独立任务实施；路径漂移脚本不能宣称覆盖字段兼容性 |

## 6. Git 管理与提交

### 默认授权与任务分支

默认授权以 [AGENTS.md 的工作流](../AGENTS.md#codex-默认工作流) 为准：实现、验证、Commit、Push、创建 PR、PR CI 成功后合并 main、同步 main 和本地清理均自主完成。用户当次的只读、暂不提交或分支约束优先；打 tag、发布和真实业务操作仍分别授权。

- 开始检查分支、工作区、暂存区和最近提交；保护已有改动，必要时使用隔离 worktree，不自动 stash、覆盖、强推或改写历史。
- 新任务从核对过的最新 `origin/main` 建短期 `feat/`、`fix/`、`refactor/`、`docs/` 或 `chore/` 分支，同一任务复用；不将其他任务的独有提交带入 PR，不直接在 main 开发。
- 完成必要本地验证后，按独立目的 Commit 并 Push，创建目标为 main 的 PR。PR 标题与描述围绕最终改动，说明验证和真实设备等未验边界。
- 合并前确认 PR 最新 head 的适用 CI 成功；失败、取消、缺失或跳过的必要检查均不能视为通过。发生修改后只认新 head 的结果，合并绑定该 head，不绕过分支保护。
- 合并后 fetch 最新远端状态；在干净主工作区切换 main 并 `git pull --ff-only`。若原工作区有用户改动或本地主分支与远端分叉，在隔离工作树同步 main、保留旧分支/文件并明确说明，不用 reset/rebase 掩盖差异。
- 确认本地 main 与远端一致后，再清理本任务临时 worktree 和已合并的本地开发分支。主工作区仍有用户改动时不强行切换，不删除承载这些改动的分支。
- 清理 worktree 前核对绝对路径、Git 状态及未跟踪文件；将交付 APK 和需要保留的证据复制到持久位置，验证后才删除。远端分支、其他任务分支/工作树及用户文件不顺带删除。

### 什么时候 commit

原则：**一个提交表达一个独立目的，具备可理解、可验证、可回退的完整改动。** 不要求每改一个文件提交，也不把多个无关任务攒到一次提交。

| 情况 | 提交时机与范围 |
|---|---|
| 缺陷修复 | 问题修复、对应回归测试、必要契约/文档一起完成，相关检查通过后提交 |
| 新功能 | 按可独立验证的能力提交；复杂任务可分多个完整步骤，不提交只有调用方、没有实现等中间断裂状态 |
| 纯重构 | 与行为变更分开；先证明行为保持，再提交。不能只为了拆提交把依赖代码拆断 |
| 文档/工具/目录清理 | 按同一个维护目的提交；文件删除、引用更新、工具测试与 CI 接入保持一致，避免提交后留下断链 |
| 发布准备 | 功能提交完成后，版本号、CHANGELOG、README、产物校验形成独立 `chore(release): X.Y.Z`；APK 留在 dist，不入 Git |
| 用户明确要求保存未完成进度 | 可在开发分支提交 `chore(wip): ...`，正文列出失败检查、未完成项与阻塞；不能标为完成、合入 main、打发布 tag 或覆盖 dist |

普通提交须通过第 2 节规定的相关检查。真实支付/现场条件尚未具备时，可提交已验证的实现与明确的限制，但不能声称业务已验或已具备发布条件；若本次要求的验收尚未满足，任务仍未完成。
已知编译/单测/仓库检查失败、包含敏感数据或夹带无关改动时，不做普通完成提交。WIP 也不得包含敏感数据。

开发 commit 与发版分开：不为每个中间提交消耗版本号；需要交付 APK 时，按第 3 节为最终内容准备新版本，同版本已发布产物不得覆盖。

### 提交前检查

1. 按实际影响运行第 2 节检查；同步相关文档与 CHANGELOG 的 Unreleased。检查输出要对应将要提交的内容，之后有实质修改须重验相关项。
2. 用 `git add -- <明确路径>` 或 `git add -p` 只暂存本次已核对的改动，包含必要的新文件与删除；不默认 `git add .` / `git add -A`，不夹带用户或其他任务的改动。
3. 检查 `git diff --cached --stat`、`git diff --cached`、`git diff --cached --check`，确认依赖文件齐全、无密钥/账号数据/本机配置/产物。既有 CRLF 文件可在本次检查中设置 `core.whitespace=cr-at-eol`，不为此批量改行尾或关闭其他检查。
4. 确认暂存内容是已验证的内容。若同一文件有暂存/未暂存的不同业务改动，工作区检查通过不等于该提交通过；使用隔离工作区核验，或先把提交边界整理完整，不冒用整个工作区的验证结果。
5. 自动执行 `git commit`，再核查状态与提交差异；随后 Push、创建 PR 并按上述 CI 门槛完成合并和清理。最终报告 PR、CI、main SHA 及保留内容。

不以 commit 代替测试、评审、设备验收或发布检查；不以工作区干净作为唯一完成标准。

### 提交信息

使用 `type(scope): 中文目的`，描述最终行为，避免“更新”“修改文件”等无信息标题。

```text
fix(vm): 防止同一设备并发启动
feat(wallet): 增加充值商品选择
refactor(core): 收敛账单状态映射
docs(git): 明确提交时机与暂存区检查
chore(repo): 清理重复截图并校正引用
chore(release): X.Y.Z
```

正文按需要说明原因、实际验证命令、兼容性与未验证项；没有独立目的的修正可在尚未提交时并入本次改动，已提交后默认新增修正提交。
