> 原 APK 分析及既有网络核查未发现公开 API 文档。2026-10-23 补充原应用更新通道、签名样本与版本门禁实测；未重验下表文档地址。项目以静态依据与脱敏实测维护契约。

## 2. 契约文件：[`api-contract.json`](api-contract.json)

结构：

| 字段 | 说明 |
|---|---|
| `baseUrl` / `headers` | 网关地址与当前 4 个请求头；`VersionCode=3.1.9` 是官方版本名，与本客户端发布版本独立 |
| `envelope` | `{code,msg,data,size,time}` |
| `errorCodes` | `-1/-2/-17/-18/-20/-28/-52/-87/-88/-98/-99` 的语义（客户端实测 + 静态确认） |
| `endpoints[]` | 本项目使用的 **31** 个端点：方法、路径、参数、响应模型、用途、验证等级（`live` / `live-error-path` / `static`） |
| `baseline.paths` | 基线 APK（v3.1.5）中静态可见的 **全部 106** 条 `/api/v1` 路径 |
| `outOfScopePaths` | 明确不迁移的业务族（考勤、IC 卡、云卡、E 袋洗、驾考…） |

产物中 `verified` 字段刻意区分：

- `live`：既有采集中用真实请求（含用户账号）确认过，不代表当前重新执行；
- `live-error-path`：只验证了匿名/错误路径（如验证码错误、无令牌 `-99`）；
- `static`：仅由反编译确认，尚未产生真实业务数据。

## 3. 变更检测：[`tools/api-diff.py`](../tools/api-diff.py)

当官方发布新版本时，先运行路径检测，再按结果决定是否需要反编译或运行时分析：

```powershell
python tools\api-diff.py "慧生活798-新版本.apk"
```

脚本直接读取 APK 内所有 DEX 的字符串表（不执行代码、不加载资源），提取 `/api/v1/*` 并对比基线：

```
APK paths     : 106
Baseline paths: 106
Contract uses : 31

No drift detected.
```

输出三类差异：

| 标记 | 含义 | 处理建议 |
|---|---|---|
| `[NEW]` | 新版本新增的路径 | 核对是否影响现有范围；新增业务需独立立项，不自动实现 |
| `[REMOVED]` | 基线里有、新版本没了 | 客户端若在用会 404，需下线或替换 |
| `[BREAK]` | 本项目在用的端点在新版本中消失 | 立即修客户端 |

退出码 `1` 表示有漂移，需人工复核（`--allow-drift` 只能用于查看，不能当作验收通过）。`--dump` 可导出最新路径清单。

### 局限（必须知道）

1. 只比较**路径字符串**，不比较参数/字段：字段级变化需要对比 bean（`com.ilife.lib.coremodel.data.bean.*`）或抓包。
2. 混淆/字符串加密/加固会让路径不可见：可能报大量 `[REMOVED]` 或 `No /api/v1 paths found`。这不表示路径已删除，也不是兼容性通过；3.1.9 只能看到加固壳，需可分析样本或运行时证据，不能用空列表替换 baseline。
3. 契约只覆盖客户端静态可见的接口，服务端内部接口无法从 APK 得到。

## 4. 运行时契约探针（无文档时的第二道保险）

客户端内置「测试接口连通性」（我的 → 服务端连接），实际请求 `GET /api/v1/ui/app/master`，展示：

- `code=0` 与「已登录数据 / 匿名数据」判定；
- 收藏数量。

这能第一时间发现：网关不可达、信封结构变化、令牌语义变化。登录页每次进入都会向 `/api/v1/captcha/` 取新图，也是天然的连通性证据。

需要更细的探针时，可直接用 curl（匿名只读）：

```bash
curl -s -H 'ApplicationType: 1,1' -H 'VersionCode: 3.1.9' \
     -H 'user-agent: Android_ilife798_3.1.9' \
     https://i.ilife798.com/api/v1/ui/app/master
# {"code":0,"data":{"ads":[]},"time":...}
```

## 5. 建议的升级流程

1. `python tools/api-diff.py 新APK.apk` → 看是否有 `NEW/REMOVED/BREAK`；
2. 有变化时，用 JADX 只反编译相关接口类（`c4/*.java`、`d4/*.java`）确认参数与响应；
3. 根据已核实的参数/响应更新 `docs/api-contract.json`；只有完整提取并审查过新样本路径，才单独升级 `baseline.paths`，不得为通过检测接受新 baseline；
4. App 内跑「连通性自检 + 一次真实设备详情」，确认字段未变；
5. 若出现正式文档，与实际服务端和原样本交叉核对后更新契约；baseline 仍用于 APK 路径漂移，不混入其他版本。

## 6. 原 APK 版本与更新通道

### 2026-10-23 核实结果

- 当前可获得的最新 Android 原版为 **3.1.9 / 31009**，包名 `com.cloudora.android`；[小米应用商店](https://app.mi.com/details?id=com.cloudora.android)列出同版本。通过[分发页](https://www.ppzy.com/app/5760.html)下载，最终地址为华为 CDN `https://appdl-1-drcn.dbankcdn.com/dl/appdl/application/apk/e7/e732ddf4d0444a619bce3979083b49eb/com.cloudora.android.2609221407.apk`。CDN 节点/临时链接可能变化，后续从分发入口重新取得，不能仅凭文件名认定版本。
- 本地保留 `慧生活798-3.1.9.apk`（忽略、不提交），60,417,620 字节，SHA-256 `55cf45c54a983340c9329e1cca499975b27bfe4b1061ccc33b2fd9a3972297ea`。
- `apksigner verify --print-certs` 验证成功，签名证书 SHA-256 为 `ab264d1794220760f2f41b9b861d93dbd6e879182ceb9e87be69f2e698b69f39`，与仓库 3.1.5 原样本及取得的 3.1.7 一致。未安装或执行新原 APK，也不使用其私钥。
- 3.1.7 未加固样本中 `ApiClient.b()` 仍以官方版本名生成 `VersionCode` / `Android_ilife798_<version>`；`j4.e` 的 `dev/start` 仍为 `did/upgrade/ptype/args/rcp/cnt`，无需改 URL 到 `/api/v3`、无需改变 `upgrade=true` 或 `rcp=false`。
- 路径检测：3.1.7 为 104 条，对比旧基线新增 `acc/basic/auth-acc`、`ep/auth-view`、`ic/sync-dev`，移除 5 条账号认证/内部消息旧路径，本项目使用的路径未报 `[BREAK]`。未据此迁移范围外业务。
- **3.1.9 已加固**：仅一个 DEX，可见 `com.antsafe.sec.wrapper` 与 `libzxprotect.so`，静态检测退出 1，输出 `No /api/v1 paths found`。这不是完整协议审查通过。保留 3.1.5 的 106 条 baseline；当前只升级已核实的版本标识及更新参数，并用本项目链路实际验证，未宣称恢复了 3.1.9 全部参数/字段。

### 原应用的更新接口

3.1.5 的 `c4/m.java`、`BaseAppUpdateActivity.g0()` 及版本名工具表明：

```text
GET /api/v1/sys/app/upt?appid=com.cloudora.android&version=<官方 versionName>&type=1
ApplicationType: 1,1
VersionCode: <官方 versionName>
user-agent: Android_ilife798_<官方 versionName>
```

`appid` 是原包名，`type=1` 是 Android；不是自研包名、数字 versionCode 或本客户端 1.x 版本。`Api.appUpdate()` 已补齐三个参数，供原协议查询，不作为自研客户端下载安装更新入口，也不自动安装原应用。缺参实测为 `code=-1 / 请求参数错误`。

2026-10-23 匿名以 `version=3.1.5` 及 `3.1.5`/`3.1.7` 版本头查询，均返回 `code=-1 / 当前版本不需要更新`，但 3.1.5 的启动已被拒绝，应用商店存在 3.1.9。该通道可能存在发布配置或渠道差异，具体原因未核实；不能当作最新版本的唯一来源。原模型 `LatestVersionData` 含 `downloadUrl` 等字段；本次未取得成功更新载荷，不能声称该接口当前能下发下载链接。3.1.9 加固样本内是否调整此通道尚未静态核实。

以完整参数、3.1.9 请求头查询当前版本也返回相同“无需更新”；该结果只记录通道响应，不能补足加固包的字段审查。客户端 1.6.1 使用 3.1.9 标识的真实饮水机回归已完成，见 docs/05 第 8 节。

### 后续故障排查

| 现象 | 先核对 | 处理与边界 |
|---|---|---|
| 详情可读，点击使用却提示升级 | 启动原始 `code/msg`、实际 `VersionCode` 与 User-Agent 是否同一已核实官方版本 | `code=-1` 并非专用版本码；不要只改发布版本、伪造更高版本、删 `upgrade` 或把失败改成成功 |
| 官方查询说无需更新，使用仍被拒绝 | 三个查询参数、原应用分发页/商店版本、下载包内部版本与证书 | 交叉核验渠道；不要让返回值自动改写请求头或自动重试启停 |
| 新样本出现签名变化、无路径或大量移除 | 下载是否为原包、完整 APK 是否有效、是否加固 | 停止自动接受基线；保留旧样本，取得可分析样本或运行时证据后再审查 |
| 升级标识后仍提示升级/出现 404/解析失败 | 是否装了旧 APK、网关/路径/字段是否另有变化 | 用安装包实际版本与本次日志定位；不能仅根据商店版本断言整套协议兼容 |
| 启动返回 `code>=0`，仍显示待机 | `data` 信封、`rcp=false`、同设备状态快照及确认窗口 | 受理不等于执行；不得重复启动“试一试”，超时保留未知状态；结束后再核对状态与账单 |
| 令牌失效或存在未付账单 | `-99` 与 `-52/-88/-87` 的具体业务含义 | 按现有会话/账单流程处理，不归咎于版本、不为回归发短信或制造支付 |

每次升级顺序：保存样本来源/时间/大小/哈希 → 校验包名、内部版本、签名 → 路径与相关字段审查 → 同步 `Api.CLIENT_VERSION`、契约和本节 → 单测/构建/lint → 演示隔离 → 经具体授权的单次真实启停及结束状态核对。记录应区分“发布版本 / 官方协议标识 / 静态基线”；日志只保留白名单状态摘要，不保存 token、完整账号、签名订单或原始 SDK result。网络超时不能自动重试有副作用的请求。

## 本地分析工具

在仓库根目录运行，Python 3.10+、仅标准库；提取/DEX 工具默认路径相对脚本所在仓库；漂移工具在仓库根目录执行，不依赖固定盘符。

```powershell
python tools/extract.py                         # 原样本 → _extract/
python tools/dexstrings.py                      # _extract/classes*.dex → dexmeta/
python tools/api-diff.py .\慧生活798.apk
```

提取脚本可传 `--output`；DEX 工具可传 `--input` / `--output`。需要反编译源码/资源时按 docs/01 的 jadx 命令生成。
无调用方字段转储不作为契约；字段依据在原样本、反编译源码与维护中的 JSON 契约。
路径漂移检测退出 1 需人工核对，不能用 `--allow-drift` 代替审查；该工具尚不验证字段兼容性。
